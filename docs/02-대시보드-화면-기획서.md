# 자동매매 대시보드 화면 기획서

작성일 2026-11-13 · 버전 0.3 · 대상: 화면 개발자, 백엔드 개발자
데이터 계약의 기준은 `agent_trading_core/audit.py`(ScreenRun, CandidateRecord, FilterResult, DecisionRecord, EvidenceItem), `memory/log.py`(메모리 로그 엔트리), `backtest.py`(BacktestSummary)다. 화면이 보여주는 모든 숫자와 문장은 이 기록에서 나오고, 화면에서 재계산하지 않는다.

---

## 0. 원칙

1. **근거 없는 숫자는 없다.** 모든 선정·탈락·등급·주문은 "어떤 규칙이 어떤 값을 어떤 임계와 비교해 어떻게 판정했는지"까지 펼쳐 볼 수 있어야 한다.
2. **REVIEW는 눈에 띄게.** 에이전트가 읽을 수 없는 결정을 냈으면 Hold처럼 숨지 않고 별도 큐에 뜬다.
3. **하드 룰 개입은 항상 표시.** 에이전트가 Buy를 냈는데 한도 때문에 비중이 줄었거나 막혔으면, 원안과 최종안을 나란히 보여준다.
4. **시점 표시.** 모든 데이터 카드에 as-of 날짜가 붙는다. 백테스트 화면은 그 날짜 이후 정보를 절대 보여주지 않는다.
5. **자동 실행, 사람은 예외만.** 기본 운용 모드는 자동 매매다(v0.3). 화면은 읽기 전용이 기본이고, 쓰기 동작은 긴급 정지(전 화면 상단), 예외 처리(결정·실행 화면), 규칙·모드 변경(설정 화면) 세 가지뿐이며 모두 확인 단계를 거치고 감사 로그에 남는다.

## 1. 정보 구조

```
[홈]
 ├ 1 오늘 요약            ← 포트폴리오 상태 · 리스크 한도 · 오늘 자동 실행 · 예외 알림
 ├ 2 종목 선별            ← ScreenRun 목록 → 상세(깔때기·후보표) → 종목 상세
 ├ 3 결정·실행            ← DecisionRecord + 주문 상태 · 예외 큐 · 하드룰 개입
 ├ 4 종목 상세            ← 정체 · 검증 스냅샷 · 선별 이력 · 결정 이력 · 증거 · 교훈
 ├ 5 포지션·리스크         ← 보유 · 손절/트레일링 · Protections 잠금 · 섹터 노출
 ├ 6 성과·백테스트         ← 등급별 알파 · 적중률 · 정산 로그 · 반성 피드
 └ 7 설정·감사 로그        ← 규칙 파라미터 · 모델 · 변경 이력
```

사이드바 고정 네비게이션. 상단에 **데이터 기준일(as-of)** 과 **마지막 실행 시각**, **잠금 상태 배지**(Protections 발동 중이면 빨간 배지), **운용 모드 배지**(자동 실행 중 / 정지됨 / 모의투자)와 **긴급 정지 버튼**을 항상 노출한다. 사이드바의 결정·실행 메뉴에는 예외 큐 건수를 빨간 배지로 단다.

## 2. 화면별 기획

### 화면 1. 오늘 요약 (홈)

**사용자 질문**: 지금 내 포트폴리오는 어떤 상태이고, 오늘 시스템이 무엇을 자동으로 실행했고, 내가 봐야 할 예외가 있는가? (v0.3: 선별·결정 중심에서 포트폴리오·리스크 중심으로 바꿈)

위에서 아래 순서가 우선순위다.

| 영역 | 구성 | 데이터 |
|---|---|---|
| 상태 바 | 기준일, 마지막 선별·결정 시각, 잠금 배지, 운용 모드 배지, 긴급 정지 버튼 | ScreenRun.recorded_at, DecisionRecord.recorded_at, Protections·실행 레이어 상태 |
| KPI 타일 6개 | 평가 금액 / 오늘 실현 손익 / 미실현 손익 / 드로다운(한도 대비) / 그로스 노출·현금 비중 / 오늘 주문 금액(자동 실행 한도 대비) | 포지션·체결 기록, 룰 레이어 |
| 예외 알림 띠 | 예외 큐에 1건 이상이면 빨간 띠로 첫 건 요약 + "예외 큐 열기". 0건이면 숨김 | 예외 큐 |
| 오늘 자동 실행 | 시각·종목(코드 태그 + 종목명 2줄)·방향·수량·체결가·금액·상태(체결/부분 체결/차단/거부/예외)·사유·적용 룰. 상단에 파이프라인 요약(선별 → 결정 → 체결·차단·예외 건수) | 주문·체결 기록 + DecisionRecord.hard_rule_overrides |
| 리스크 한도 | 드로다운·일일 손실·오늘 주문 금액·섹터 노출을 한도선과 함께 게이지로. 한도 도달 항목은 빨강 | 룰 레이어 |
| Protections · 손절 근접 | 4종 상태 한 줄씩 + 손절선 2% 이내 종목 수 | 룰 레이어, 포지션 |
| 최근 정산 | 최근 5건: 티커·결정일·등급·실현수익·알파 | 메모리 로그 settled 엔트리 |

등급별 성과·알파 추이 차트는 홈에서 빼고 화면 6에만 둔다.

빈 상태: "오늘 선별이 아직 실행되지 않았습니다 · 마지막 실행 {날짜}". 오류 상태: 데이터 벤더 장애면 어떤 벤더인지 명시(VendorUnavailableError 메시지 그대로).

### 화면 2. 종목 선별

#### 2-A. 선별 실행 목록
- 표: 실행 ID · 기준일 · 유니버스 · 유니버스 크기 · 통과 수 · 규칙 수 · 실행 시각.
- 필터: 기간, 유니버스. 정렬: 기준일 내림차순.
- 행 클릭 → 2-B.

#### 2-B. 선별 실행 상세 (핵심 화면)

**사용자 질문**: N개 중 왜 이 15개가 남았고, 나머지는 어느 규칙에서 떨어졌나?

```
┌ 헤더: KOSPI200+KOSDAQ150 · 2026-11-12 · 350 → 15 ──────────────────────┐
│                                                                          │
│  [깔때기]  350 ─price_min─▶ 342 ─listed_days─▶ 331 ─dollar_vol_top─▶ 100 │
│            ─volatility─▶ 71 ─range_stab─▶ 64 ─sector_quota─▶ 22          │
│            ─performance─▶ 15                                             │
│   각 단계 클릭 → 그 단계에서 탈락한 종목만 아래 표에 필터                 │
│                                                                          │
│  [규칙 패널]  규칙 id · 설명 · 임계값 · 이번 실행 탈락 수 · 마지막 변경일   │
│                                                                          │
│  [후보 표]  선정 ✓/✗ · 순위 · 티커 · 이름 · 점수 · 규칙1 값 · 규칙2 값 … │
│             셀 = 값 (임계) 색상: 통과 녹색 / 탈락 빨강 / 미평가 회색      │
│             탈락 종목은 첫 탈락 규칙에 아이콘, hover에 note("IPO 2026-10-03")│
│             토글: [선정만] [탈락만] [전체]   검색: 티커/이름                │
└──────────────────────────────────────────────────────────────────────────┘
```

| 요소 | 데이터 |
|---|---|
| 깔때기 단계 | ScreenRun.rules 순서, 단계별 통과 수 = candidates 중 해당 규칙 passed 누적 |
| 규칙 패널 | 규칙 레지스트리(설정 화면과 공유) + FilterResult.threshold |
| 후보 표 셀 | CandidateRecord.filters[i].value / threshold / passed / note |
| 점수·순위 | CandidateRecord.score, rank |
| 선정 | CandidateRecord.selected |

상호작용: 행 클릭 → 화면 4(종목 상세, 선별 탭). 열 헤더 클릭 → 정렬. 표 우상단 "CSV 내보내기".

**설계 이유**: 선별이 "왜"에 답하려면 종목×규칙 행렬 전체가 보여야 한다. 통과한 종목만 보여주는 리스트는 근거가 아니다.

#### 2-C. 선별 비교 (2차)
두 실행을 골라 신규 진입·이탈 종목과 그 원인 규칙을 diff로 표시. MVP 제외.

### 화면 3. 결정·실행 (v0.3: "결정 큐"에서 이름 변경)

**사용자 질문**: 에이전트가 무엇을 결정했고, 룰이 무엇을 바꾸거나 막았고, 실제로 무엇이 체결됐고, 내가 처리할 예외는 무엇인가?

세 개 탭:

| 탭 | 내용 | 데이터 |
|---|---|---|
| 결정·실행 | DecisionRecord 전체. 카드: 티커·이름·**등급(5단계 색)**·action·확신도·진입가·손절가·사이징·논지 2줄 + **실행 상태 띠**(체결: 수량·체결가·금액·시각 / 차단: 막은 룰 / 예외: 대기 사유) | DecisionRecord + 주문·체결 기록 |
| 예외 큐 | 자동으로 주문하지 않고 사람에게 넘긴 것: REVIEW(등급 파싱 실패), 자동 실행 한도 초과로 멈춘 주문, 벤더 장애로 데이터가 빈 결정. REVIEW는 원문 전체 노출, 버튼: [재실행] [수동 등급 지정] [무시] | rating == "REVIEW", 실행 레이어 거부 사유 |
| 하드룰 개입 | 원안(에이전트) vs 최종(룰 적용 후) 2열 비교. 개입 규칙 배지 (`max_position_pct`, `sector_cap`, `protection:StoplossGuard` …) | DecisionRecord.hard_rule_overrides + 룰 레이어 출력 |

카드 펼치기 → 증거 목록(EvidenceItem: 출처 아이콘·한 줄 요약·as-of·원문 링크). 출처는 market / fundamentals / news / sentiment / macro / memory / portfolio 8종 아이콘으로 고정.

실행 흐름(자동 모드, 기본): 결정일 종가 기준 결정 → 다음 거래일 09:00 시가에 실행 레이어가 자동 주문 → 하드룰·Protections·자동 실행 한도에 걸리면 축소 또는 차단하고 사유를 기록 → 예외는 주문하지 않고 예외 큐와 알림으로. 승인 버튼과 승인 모달은 없다.

수동 승인 모드(설정에서 전환 시에만): 카드에 [승인] 버튼이 생기고 주문 요약 모달(종목·방향·수량·예상 금액·적용된 룰) → 확인 → 실행 레이어로 전달.

긴급 정지: 상단 버튼 → 확인 모달(영향: 신규 주문 중단, 미체결 주문 취소 건수, 보유 포지션 유지 / 옵션: 손절·트레일링 청산 계속 작동 여부 / 정지 사유 입력) → 확인. 다시 켜기는 관리자만, 설정 화면에서.

### 화면 4. 종목 상세

**사용자 질문**: 이 종목에 대해 시스템이 무엇을 알고, 무엇을 결정해 왔고, 그 결과는 어땠나?

상단 고정: 티커 · 회사명 · 업종 · 거래소 (identity 결과) · 현재 보유 여부 · 최근 등급.

탭:

| 탭 | 구성 | 데이터 |
|---|---|---|
| 검증 스냅샷 | 최신 OHLCV 표 · 지표 11개 표 · 최근 30 종가 미니 차트. 상단에 "이 표가 에이전트에게 주어진 유일한 숫자 출처" 안내 | snapshot.build_verified_market_snapshot 출력(저장본) |
| 선별 이력 | 날짜별 선정/탈락 타임라인. 탈락 시 어느 규칙·값 | ScreenRun → CandidateRecord |
| 결정 이력 | 날짜별 등급 띠(5색) + 카드. 카드: 논지 · 증거 · 하드룰 개입 · 설정(모델·토론 깊이) | DecisionRecord |
| 결과·교훈 | 결정별 실현수익·알파·보유기간·정산일·반성 문단. 미정산은 "pending" | 메모리 로그 엔트리 |
| 보유 | 수량·평단·손절선·트레일링 고점·미실현 | 포지션 레이어 |

결정 카드와 결과 카드는 (ticker, trade_date)로 연결되어 나란히 놓인다.

### 화면 5. 포지션·리스크

| 영역 | 구성 | 데이터 |
|---|---|---|
| 보유 표 | 티커·수량·평단·현재가·미실현%·손절선·트레일링 고점·보유일·만료일(period) | 포지션 + 하드룰 상태 |
| 리스크 게이지 | 포트폴리오 DD(피크 대비), 그로스 노출, 섹터별 노출 vs 한도(20%) 바 | 룰 레이어 |
| Protections 패널 | StoplossGuard / MaxDrawdown / Cooldown / LowProfit 각각: 상태(정상·발동) · 발동 사유 · 해제 시각 · 최근 lookback 내 트리거 건수 | 룰 레이어 |
| 청산 사유 분포 | 최근 N건 ExitType 파이: roi / stop_loss / trailing / exit_signal / force / expired | 체결 기록 |

발동 중인 Protection은 홈 상단 배지와 동기화.

### 화면 6. 성과·백테스트

| 영역 | 구성 | 데이터 |
|---|---|---|
| 등급별 성과 표 | Buy/Overweight/Hold/Underweight/Sell: n · 방향 적중률 · 평균 알파 · (Hold는 적중률 "방향 없음") | BacktestSummary.by_rating |
| 미채점 | pending 수 · REVIEW(unscored) 수 · 보유기간 표기 | BacktestSummary |
| 백테스트 실행 목록 | run_id · 티커 수 · 날짜 격자 · 셀 수 · 실패 · 요약 | BacktestResult |
| 반성 피드 | 최신 정산 반성 문단 스트림. 티커·날짜·알파 배지 | 메모리 로그 |
| 규칙 vs 에이전트 | 같은 격자에서 룰만 돌린 결과와 에이전트 결과 비교(2차) | 두 run 비교 |

주의 문구 고정 노출: "알파는 결정일 다음 첫 종가 진입 기준 {N}거래일. 모델 샘플링 1회, 텍스트 피드 미보관으로 재현값이 아님." (backtest.render 문구 그대로)

### 화면 7. 설정·감사 로그

- 운용 모드: 자동 / 수동 승인 / 모의투자 전환(관리자). 현재 상태(실행 중·정지됨)와 정지 시각·사유. 전환은 변경 이력에 남는다.
- 규칙 레지스트리: 규칙 id · 설명 · 현재 파라미터 · 적용 레이어(선별/하드룰/실행/자동 실행) · 마지막 변경(누가·언제·이전 값). 자동 실행 레이어 규칙: `auto_daily_order_cap`(일일 주문 금액 상한), `auto_daily_loss_limit`(넘으면 자동 정지), `auto_order_max`(주문당 상한), `kill_switch_reset`(재가동 권한).
- 모델 설정: 프로바이더·모델(quick/deep)·토론 라운드·출력 언어. DecisionRecord.settings와 동일 키.
- 변경 이력: 모든 파라미터 변경을 append-only로. 화면 2·3의 "마지막 변경일"이 여기를 참조.
- 데이터 경로·캐시 상태: 캐시 디렉터리 크기, 심볼별 마지막 다운로드 시각, 벤더 도달성.

## 6. 비기능

- **갱신**: 선별·결정은 하루 1~2회 배치라 폴링 60초면 충분. 포지션·리스크는 장중 10초.
- **권한**: 조회(전원) / 승인(운영자) / 규칙 변경(관리자). 쓰기 동작은 모두 감사 로그에 남는다.
- **반응형**: 화면 2-B 후보 표는 데스크톱 전용(가로 스크롤). 나머지는 모바일에서 카드형으로 축약.
- **접근성**: 등급·통과/탈락을 색상 외 텍스트·아이콘으로 병기. 표 헤더 sticky.
- **검증 기준**(팀 규칙): 스타일 작업 완료 증거는 computed 수치 실측표(상태별)로 제출.

## 11. 추가 화면 검토 — 하드 룰·2차 실측·모의투자 반영 (2026-11-13, 제안)

하드 룰 레이어(`risk.py`), 포트폴리오 시뮬레이션(`simulate.py`, docs/05), 모의투자 통과 기준(`config.PAPER_TRADING`)이 생기면서 화면에 새로 필요한 것과 기존 화면에 채워야 할 것을 정리했다. 시안 담당이 v0.5에 반영할지 결정한다. 백엔드 계약은 이미 있다(`/api/paper`, `/api/settings/rules`의 `risk_rules`·`paper_criteria`).

### 11-1. 새 화면 — 8. 모의투자 검증 (실거래 전환 게이트)

**사용자 질문**: 모의투자가 몇 주째이고, 통과 기준 6개 중 무엇을 충족하고 무엇을 못 하는가, 실거래로 넘어가도 되는가.

| 영역 | 구성 | 데이터 |
|---|---|---|
| 기준 스코어카드 | 기준 6개 각각: 기준값 · 현재값 · 판정(충족/미충족/진행 중) · 남은 기간. 전부 충족이면 상단에 "전환 가능" | `PAPER_TRADING` + 모의 운용 기록(주문·에쿼티·결정) |
| 드로다운 게이지 | 모의 기간 에쿼티의 피크 대비 DD, 한도선 −10%와 하드 룰 선 −10%/−20% 표시 | 모의 에쿼티 |
| 위반 목록 | 일일 손실 한도 위반일, 정지 발동, REVIEW 결정, 결정 없는 주문 — 각각 날짜·값·링크 | 운영 기록 · 결정 · 주문 |
| 기대 대비 | 같은 기간 2차 실측(B·C) 재현값과 모의 결과 비교: 노출·거래 수·청산 사유 분포가 비슷한가(추적 오차) | `/api/paper` + 모의 기록 |
| 전환 버튼 | [실거래 전환] (관리자) — 전부 충족 시에만 활성, 확인 모달(기준 요약·전환 후 한도·사유) → `POST /api/trading/mode {auto}` | 운영 기록 |

왜 별도 화면인가: 실거래 전환은 이 시스템에서 가장 되돌리기 어려운 결정이고, 성과 화면(과거 분석)이나 설정 화면(파라미터)과 질문이 다르다. 우선순위는 **2차**(모의투자 시작 전).

### 11-3. 공통 컴포넌트 추가

- **한도 게이지**: 현재값 · 한도선 1~2개 · 한도 도달 시 빨강. 홈·화면 5·화면 8이 같이 쓴다.
- **청산 사유 배지**: 손절 / 트레일링 / 기간 만료 / 등급 하향 / 정지 청산 5종(`exit_reason_ko`). 매도 사유 배지(§9 v0.2, 7종)와 다르다: 매도 사유는 에이전트의 판단, 청산 사유는 룰의 판정.
- **국면 배지**: KOSPI ≥ 200일선 "위험 자산 매수 가능" / 아래 "신규 매수 없음".
